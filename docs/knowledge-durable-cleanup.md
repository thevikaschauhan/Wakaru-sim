# Durable withdrawal-bound cleanup receipts

Local candidate only. `cart_recovery.domain.cleanup.create_cleanup_app` is default-off and is not mounted by startup. Migration 003 must be explicitly applied after migrations 001 and 002. No production grant, scheduler, deployment or aggregate acknowledgment is added.

The separate `wakaru-knowledge-cleanup` audience exposes `purge` and `receipt` under `/internal/integrations/knowledge-cleanup/`. Both use the same immutable command body, validated by `contracts/knowledge/cleanup-v1/request.schema.json`: command UUID, exact Engine scope, acknowledged withdrawal UUID/hash and expected data version. Responses bind the full request digest. Exact operation and tenant/store grants are required; receipt access also requires purge permission. Responses use the existing no-store response helper.

Under the store's exclusive control lock, the receiver checks the matching `withdraw_source` delivery receipt and the current non-erased scope. If the expected version is current, it runs the existing physical purge helper and inserts a retained receipt in the same transaction. Source/dependent-assertion removal, tombstones, data version and receipt all commit together or all roll back. If only the expected version differs, it records a terminal `refused` receipt with zero removals. Other scope, quarantine, proof, schema or database failures do not create success/refusal receipts.

`knowledge_retained.cleanup_receipts` retains HMAC scope/command keys, request/scope digests, terminal status and counts/version. SQL guards reject updates, deletion and truncation. Exact replays return the same result; changed bytes under the same scope/command ID are refused. Lookup works after subject erasure because it validates the historical binding without requiring current active data. Missing receipts are `unknown`, never permission to repeat an uncertain attempt. A recorded refusal allows Engine to choose a new command only after an independent current-version read.

These receipts prove a historical active-row purge, not backup/WAL/media disposal or whole-application privacy completion. The existing retained export/checkpoint envelopes do not yet carry this new ledger. Engine's companion migration 082 stores its own RLS-protected cleanup outbox and terminal results, while C5 completion remains blocked. Complete inventory/export/recovery, runtime role/key custody, hosted/native AMD64 and new forward/rollback artifacts remain rollout gates.

Local tests cover physical dependent-object deletion, atomic rollback if receipt insertion fails, concurrent versions, durable refusal/replay, erasure/quarantine boundaries, immutable metadata and authenticated operation/tenant binding. Engine's separate real HTTP fixture loses successful withdrawal/purge replies to qualify restart reconciliation and the prohibition on replay after a crash before HTTP.
